Create two new controllers by following the Instagram auth controller patterns exactly, adapted for X OAuth 2.0 with PKCE.

**TwitterAuthController** (organization accounts) -- follow InstagramAuthController pattern:

Module: `ClippsterServerWeb.TwitterAuthController`
Aliases: ClippsterServer.Social, ClippsterServer.Social.Platforms.Twitter, ClippsterServer.Organizations, ClippsterServer.Accounts

`start_oauth/2` - GET /api/auth/twitter/start
  - Required params: organization_id, callback_port, auth_token
  - Verify auth token via Accounts.verify_token/1
  - Verify user is org admin via Organizations.is_admin?/2
  - Read config from Application.get_env(:clippster_server, :twitter_oauth, [])
  - Build server_callback_url: ClippsterServerWeb.Endpoint.url() <> "/api/auth/twitter/callback"
  - Build state map: %{org_id, callback_port, user_id, timestamp: System.system_time(:second)}
  - Call Twitter.authorize_url/1 with opts: %{client_id: config[:client_id], redirect_uri: server_callback_url, state: state_map}
    NOTE: The Platform module's authorize_url/1 handles PKCE generation and state encoding internally (code_verifier is merged into state inside authorize_url)
  - Redirect to returned auth_url

`oauth_callback/2` - GET /api/auth/twitter/callback
  - Receives code and state params from X redirect
  - Decode state (Base64 URL decode -> JSON decode)
  - Extract org_id, callback_port, user_id, code_verifier from decoded state
  - Validate timestamp (reject if > 600 seconds old)
  - Call process_oauth_callback/5

`process_oauth_callback/5` private function:
  - Read twitter_oauth config for client_id, client_secret
  - Get user via Accounts.get_user/1
  - Call Twitter.exchange_code(code, %{client_id:, client_secret:, redirect_uri: server_callback_url, code_verifier: code_verifier})
  - On success: Call Twitter.get_user_profile(token_data.access_token)
  - On profile success: Build account_attrs with platform: "twitter", platform_user_id, username, display_name, profile_image_url, access_token, refresh_token (CRITICAL: include refresh_token unlike Instagram which doesn't have one), token_expires_at: calculate_expiry(token_data.expires_in)
  - Call Social.create_social_account(org_id, account_attrs, user)
  - Handle unique constraint (update existing via Social.update_existing_account)
  - Redirect to Tauri callback: "http://localhost:#{callback_port}/twitter-callback?#{success_params}"
  - Error case: redirect with error params

Include same helper functions as Instagram controller: decode_state/1, redirect_with_success/3, redirect_with_error/3, calculate_expiry/1, format_error/1, serialize_account/1, has_unique_constraint_error?/1

IMPORTANT: redirect_with_success and redirect_with_error should use path "/twitter-callback" (not "/instagram-callback").

**UserTwitterAuthController** (personal/clipper accounts) -- follow UserInstagramAuthController pattern:

Module: `ClippsterServerWeb.UserTwitterAuthController`
Aliases: ClippsterServer.Campaigns, ClippsterServer.Social.Platforms.Twitter, ClippsterServer.Accounts

`start_oauth/2` - GET /api/auth/user-twitter/start
  - Required params: callback_port, auth_token (no organization_id)
  - Verify auth token
  - Build state: %{user_id, callback_port, timestamp}
  - Call Twitter.authorize_url/1 with server callback: "/api/auth/user-twitter/callback"
  - Redirect to auth URL

`oauth_callback/2` - GET /api/auth/user-twitter/callback
  - Decode state, extract user_id, callback_port, code_verifier
  - Validate timestamp
  - Call process_oauth_callback/4

`process_oauth_callback/4`:
  - Exchange code with code_verifier
  - Get profile
  - Build attrs with platform: "twitter", include refresh_token
  - Use Campaigns.create_social_account/2 or update via create_or_update_account/2 (same as UserInstagramAuthController)
  - Redirect to "http://localhost:#{callback_port}/twitter-callback?#{params}"

Include same helpers as UserInstagramAuthController.

  <name>Task 3: Update TokenRefreshWorker for X 2-hour token expiry</name>
  <files>server/lib/clippster_server/social/token_refresh_worker.ex</files>
  <action>
Update the TokenRefreshWorker to handle X's 2-hour token expiry alongside Instagram's 60-day expiry.

Two changes needed:

1. **Reduce check interval from 12 hours to 1 hour:**
   Change `@default_interval :timer.hours(12)` to `@default_interval :timer.hours(1)` on line 15.

   Rationale: X tokens expire in 2 hours. Checking every 12 hours would miss most expirations. 1-hour checks catch X tokens at the 1-hour mark (50% lifetime), leaving a full hour buffer. Instagram tokens (60-day expiry) still work fine with hourly checks -- they'll just be detected earlier and refreshed when they're within 1 day of expiry (existing threshold in get_accounts_needing_refresh).

2. **Update refresh_account_tokens to handle single-use refresh token rotation:**
   The existing code on lines 128-133 already handles this correctly:
   ```elixir
   attrs = if new_tokens[:refresh_token] do
     Map.put(attrs, :refresh_token, new_tokens[:refresh_token])
   else
     attrs
   end
   ```
   This means if the platform returns a new refresh_token (as X does), it gets stored. No code change needed here.

3. **However, the current code passes `access_token` to `refresh_tokens/1` (line 112), but X's refresh needs the `refresh_token`:**
   Current code: `platform_module.refresh_tokens(access_token)`

   The Platform behaviour callback signature is `refresh_tokens(refresh_token :: String.t())` -- it expects a refresh token. But the current worker reads `access_token = SocialAccount.get_access_token(account)` and passes that.

   Fix: Update refresh_account_tokens/1 to read BOTH tokens and pass the appropriate one based on platform:
   - For platforms with refresh_token_encrypted (like Twitter), decrypt and use the refresh_token
   - For platforms without (like Instagram where refresh_tokens/1 takes the access_token), continue using access_token

   Implementation:
   ```elixir
   defp refresh_account_tokens(%SocialAccount{} = account) do
     Logger.info("[TokenRefreshWorker] Refreshing tokens for account #{account.id} (#{account.platform})")

     # Some platforms (Instagram) refresh using access_token
     # Others (Twitter/X) refresh using refresh_token
     token_for_refresh = case SocialAccount.get_refresh_token(account) do
       {:ok, refresh_token} when is_binary(refresh_token) and refresh_token != "" ->
         refresh_token
       _ ->
         case SocialAccount.get_access_token(account) do
           {:ok, access_token} -> access_token
           _ -> nil
         end
     end

     # ... rest of function uses token_for_refresh instead of access_token
   ```

   Wait -- check what SocialAccount.get_access_token and get_refresh_token actually return. They call TokenEncryption.decrypt/1. Check if decrypt returns {:ok, value} or just value. Looking at the code:
   ```elixir
   def get_access_token(%__MODULE__{access_token_encrypted: encrypted}) do
     TokenEncryption.decrypt(encrypted)
   end
   ```

   The return type depends on TokenEncryption.decrypt. Handle both patterns (may return {:ok, token} or raw token or nil for nil input).

   Updated approach -- handle nil encrypted field and decrypt result:
   ```elixir
   defp get_token_for_refresh(%SocialAccount{} = account) do
     # Try refresh_token first (needed for X/Twitter single-use rotation)
     case account.refresh_token_encrypted do
       nil ->
         SocialAccount.get_access_token(account)
       _encrypted ->
         case SocialAccount.get_refresh_token(account) do
           {:ok, token} when is_binary(token) and token != "" -> token
           token when is_binary(token) and token != "" -> token
           _ -> SocialAccount.get_access_token(account)
         end
     end
   end
   ```

   Then use `get_token_for_refresh(account)` instead of `SocialAccount.get_access_token(account)` in refresh_account_tokens/1.

Also update the Logger.info message in init/2 to handle the case where interval is less than an hour (show minutes).
