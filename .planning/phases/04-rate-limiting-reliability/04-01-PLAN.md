<objective>
Implement X API reliability infrastructure: a centralized HTTP client with exponential backoff retry for transient failures, rate limit header parsing and quota tracking, and PulseKit logging for all API interactions.

Purpose: Without retry logic, transient X API failures (429, 5xx) cause permanent post failures. Without rate limit tracking, the system has no visibility into quota consumption. Without logging, debugging failed posts is impossible.

Output: TwitterApiClient module (retry wrapper), TwitterRateLimiter module (quota tracking), database migration for rate_limit_states table and content_hash column.
</objective>

**Step 2: Create the database migration.**

Generate migration: `mix ecto.gen.migration add_reliability_fields`

The migration should:
1. Create `rate_limit_states` table with fields:
   - `id` (bigserial primary key)
   - `endpoint` (string, not null) - e.g. "/2/tweets", "/2/media/upload"
   - `social_account_id` (references social_accounts, nullable) - per-user tracking
   - `limit_value` (integer) - max requests per window (named limit_value because "limit" is reserved)
   - `remaining` (integer) - requests remaining
   - `reset_at` (utc_datetime) - when window resets
   - `last_checked_at` (utc_datetime)
   - `timestamps()`
   - Unique index on `[:endpoint, :social_account_id]`

2. Add `content_hash` column (string, nullable) to `post_submissions` table.
   - Add index on `[:organization_social_account_id, :content_hash]` for duplicate lookups.

Run `mix ecto.migrate`.

**Step 3: Create TwitterRateLimiter module** at `server/lib/clippster_server/social/twitter_rate_limiter.ex`.

Create an Ecto schema `ClippsterServer.Social.RateLimitState` embedded in the same file (or a separate schema file at `server/lib/clippster_server/social/rate_limit_state.ex` if preferred - keep it in the same file for simplicity).

Module: `ClippsterServer.Social.TwitterRateLimiter`
- `update_from_response(endpoint, social_account_id, headers)` - Parse `x-rate-limit-limit`, `x-rate-limit-remaining`, `x-rate-limit-reset` from response headers. Upsert into `rate_limit_states` table using `Repo.insert/2` with `on_conflict: :replace_all` and `conflict_target: [:endpoint, :social_account_id]`.
- `check_quota(endpoint, social_account_id, threshold \\ 10)` - Query rate_limit_states for the endpoint. Return `:ok` if remaining > threshold, `{:warning, remaining, reset_at}` if remaining < threshold but > 0, `{:error, :rate_limited, reset_at}` if remaining == 0 and reset_at is in the future. If no record exists, return `:ok` (first request).
- Private `parse_header/2` to find header by lowercase name.
- Private `unix_to_datetime/1` to convert Unix timestamp to DateTime.

**Step 4: Create TwitterApiClient module** at `server/lib/clippster_server/social/twitter_api_client.ex`.

Module: `ClippsterServer.Social.TwitterApiClient`

This wraps HTTPoison calls with retry logic, rate limit parsing, and PulseKit logging. Uses the `retry` library's `retry/2` macro.

Public functions:
- `get(url, headers, opts \\ [])` - GET request with retry
- `post(url, body, headers, opts \\ [])` - POST request with retry
- `request(method, url, body, headers, opts \\ [])` - Generic request with retry

The `request/5` function should:
1. Check rate limit quota via `TwitterRateLimiter.check_quota/3` if `opts[:endpoint]` and `opts[:social_account_id]` provided. If `{:error, :rate_limited, reset_at}`, return `{:error, {:rate_limited, reset_at}}` immediately without making the request.
2. Use `retry with: exponential_backoff() |> randomize() |> cap(60_000) |> expiry(300_000)` block.
3. Inside retry: call `HTTPoison.request(method, url, body, headers, http_opts)` where http_opts come from `opts[:http_options]` or default `[timeout: 30_000, recv_timeout: 30_000]`.
4. After getting response, call `process_response/3` which:
   a. Parses rate limit headers via `TwitterRateLimiter.update_from_response/3` (if endpoint + social_account_id in opts)
   b. Logs via `pulse_capture/1` with type "x_api_call", endpoint, method, status, rate_limit metadata, duration_ms, error info
   c. For transient errors (429, 500, 502, 503, 504): raise a `RetryableError` to trigger retry
   d. For permanent errors (400, 401, 403, 404): return `{:ok, response}` (let caller handle)
   e. For success (2xx): return `{:ok, response}`
5. The `after` clause returns `{:ok, response}`, the `else` clause returns `{:error, :max_retries_exceeded}`.
6. For 429 responses, check for `Retry-After` header and respect it by sleeping that duration before retry.

Important: Do NOT switch existing Twitter module to use TwitterApiClient in this task. That wiring happens in Plan 02. This task only creates the modules.

Define a simple exception `RetryableError` (can be inline `defexception` in the module) to signal retryable failures.

Include `pulse_capture/1` helper matching the existing pattern in ScheduledPostWorker (check `Code.ensure_loaded?(PulseKit)`, try/rescue).
